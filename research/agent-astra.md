# Independent energy and architecture assessment

Research date: 2026-10-07. Source review only. I did not profile the running app, run CPU benchmarks, inspect live user data, or alter the app. This report separates behavior established by the checked-out source from its unmeasured energy consequences.

My recommendation is to start with the V2-compatible TypeScript/OpenTUI fork, retain T3's existing server and client contracts, and fix its idle timers and transcript recomputation before considering a Rust replacement. A carefully built Rust client is a strong long-term option for tight memory and latency targets. The present Rust client is not evidence that Rust automatically provides the best battery life.

The screenshot establishes only that macOS listed T3 Code Nightly under significant energy use. It supplies no watts, CPU percentage, memory, battery drain rate, or attributable cause. Apple's Energy Impact is a relative score. Its 12-hour column is an average score, not watt-hours. Neither supports a numeric claim such as "this app uses 15 W" or "a TUI saves 80%". [Apple Activity Monitor guide](https://support.apple.com/guide/activity-monitor/view-energy-consumption-actmntr43697/mac), [Apple battery-menu guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringBatteryUsage.html).

## Confirmed source behavior and plausible costs

The T3 fork inspected is `StevenMatchett/t3code` at `2a63eee2b8cba7c499ff98c9537a1942b4c31309`. Tria is `Pajn/tria` at `abf467dcbc2f8263564ff9bfe3e93ae20d4c2fe1`. Their source behavior does not prove that the running Nightly binary contains the same code.

| Finding established by source | What it means | What remains unmeasured |
| --- | --- | --- |
| Tria's Rust application has a 120 ms repeating tick and unconditionally calls `terminal.draw` each main-loop iteration. Idle ticks therefore cause about 8.3 drawing computations per second. | Replace the permanent tick with an event-driven dirty flag and deadlines for actual timers. Ratatui can limit terminal output to changed cells, but calling the UI still costs CPU. | The size of this cost for a real conversation, terminal, and Mac. |
| The TS TUI has a shared 250 ms activity clock. `CompletedTiming` subscribes to that clock through `useLocalDay`. | A completed-turn label can keep the four-times-per-second clock alive even when no spinner needs animation. Split day changes from animation, scheduling the day label at the next midnight. React's snapshot comparison can suppress a render while timer and listener work still occur. | Whether this particular completed label is mounted in the user's screen, and the energy saved by changing it. |
| TS `Conversation` computes the complete loaded timeline's `conversationLines` whenever the thread identity changes, then derives the visible viewport. Markdown conversion calls `Lexer.lex` on each source passed to it. | Display virtualization alone does not bound parsing and wrapping. Cache completed items by item version, width, and theme. Recompute the active item and visible rows. | How often identity changes on actual provider streams, and how much parsing dominates. |
| V2 `turn-item.updated` does linear array searches and copies. Visible-item upsert removes/reinserts the item and renumbers rows. | Cost grows with the loaded timeline. An indexed entity map and stable ordered item IDs can avoid repeated global work. The source already avoids an earlier all-items visibility recheck for ordinary streaming changes. | Whether this is material at real loaded-page sizes. Microbenchmarks with 100,000 loaded items should be labeled a stress test. |
| The native Rust telemetry child samples in the background. Normal background and battery sampling is 5 seconds; constrained conditions use 15 seconds; normal live diagnostics on AC can use 1 second. | Closing diagnostics stops continuous delivery, not all native collection. The collector refreshes the process list with `ProcessesToUpdate::All` and retains bounded history. This overhead survives a TUI using the same server. | Actual CPU and wakeups of collection. A native implementation can still do unnecessary work. |
| The server's event-loop monitor sets a native histogram timer at 1-second resolution and reads it every 30 seconds. Port discovery has a permanent 3-second timer, with a cheap no-op when not retained. | Background work exists independently of the GUI. These are bounded candidates to inspect, not an explanation for high CPU on their own. | Their measured contribution versus provider and rendering work. |
| Desktop bootstrap state is polled every 2 seconds because the bridge exposes no change event. | An event-based bridge would avoid those reads and state updates. This particular work disappears with a standalone TUI. | Whether the poll causes appreciable downstream updates. |

There are existing safeguards worth preserving. The V2 live stream coalesces running tool updates over 50 ms and preserves terminal updates. This helper does not coalesce every event type, so it is not a general guarantee of a 20 Hz UI update limit. The client shell applies incoming batches with one state write. Resource history has explicit size bounds. Theme and settings code use filesystem notifications. A broad claim that T3 continuously polls every file or has no backpressure would be wrong. [Tool event coalescer](https://github.com/StevenMatchett/t3code/blob/2a63eee2b8cba7c499ff98c9537a1942b4c31309/apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.ts#L18), [shell batching](https://github.com/StevenMatchett/t3code/blob/2a63eee2b8cba7c499ff98c9537a1942b4c31309/packages/client-runtime/src/state/shell.ts#L158), [resource telemetry design](https://github.com/StevenMatchett/t3code/blob/2a63eee2b8cba7c499ff98c9537a1942b4c31309/docs/internals/resource-telemetry.md).

Provider subprocesses, shell commands, project builds, git checkpointing, and the orchestrator server remain when Electron is replaced. A terminal emulator also uses CPU and GPU. Measure the whole local process group plus the terminal's incremental cost, and report the provider workload separately. If a provider consumes most of the energy, a frontend rewrite has a correspondingly limited benefit. A remote T3 server can remove that local workload, but moves the energy use to another computer.

## Architecture choice

| Choice | Assessment |
| --- | --- |
| TypeScript and OpenTUI | Best starting point for preserving fast-moving Nightly/V2 behavior. It shares contracts, Effect state, auth, and reconnection logic. OpenTUI's core is native Zig, so this is already a mixed-language design. Optimize update scope and scheduling first. |
| Rust and Ratatui | Best alternative when a measured requirement calls for a small resident client and predictable allocation behavior. Use generated protocol types and recorded conformance fixtures. Keep the server authoritative. A Rust rewrite must still implement streaming order, reconnect/resume, pagination, approvals, branching, and provider compatibility. |
| C or C++ | No demonstrated advantage for this task that compensates for added protocol and UI maintenance. Consider a bounded native hot path only after profiling identifies one. Neither language fixes excessive redraws or repeated whole-history work. |

OpenTUI documents its Zig core and TypeScript/React interfaces. Ratatui documents immediate-mode rendering, where the application decides when to draw. Those designs support efficient clients, but neither makes idle scheduling automatic. The fork's own renderer decision identifies shared TypeScript state as the reason for OpenTUI and keeps the renderer behind local adapters. [OpenTUI upstream](https://github.com/anomalyco/opentui), [Ratatui rendering](https://ratatui.rs/concepts/rendering/), [T3 renderer decision](https://github.com/StevenMatchett/t3code/blob/2a63eee2b8cba7c499ff98c9537a1942b4c31309/docs/internals/decisions/0001-tui-renderer.md).

Preserve T3's clear project sidebar, readable conversation, compact tool groups, editable multiline prompt, approval controls, plan view, and diff inspection. Use spacing, semantic color, Unicode borders with fallbacks, stable scroll anchoring, and keyboard/mouse support. Browser previews and arbitrary rich web content need an external browser or an explicit reduced terminal presentation. Images depend on terminal capabilities. A terminal can preserve the workflow and visual hierarchy without promising pixel parity.

The client should wait on input, socket events, resize events, and the nearest real deadline. Keep one dirty flag. Merge streaming display work into 33-50 ms windows, flush final/approval/error states promptly, and pause cosmetic animations when unfocused. Preserve every required state transition even when intermediate visual frames are skipped. Cache completed Markdown and diff layouts. Paginate old history and retain a bounded cache. Bound websocket queues and output buffers. Avoid a second local server if one already serves the environment.

## Proposed acceptance targets

These are engineering targets for a prototype on the user's M5, not predictions or measured results.

| Scenario | Initial target |
| --- | --- |
| Connected idle client after warmup | Under 0.5% of one CPU core averaged over 5 minutes, no periodic UI redraw, at most 1 client-attributable wakeup per second apart from protocol necessities. Aim lower after identifying the required timers. |
| Streaming visible response | At most 30 visual commits per second by default; p95 input-to-visible-echo under 50 ms; p95 client state-plus-layout work under 5 ms for the agreed fixture. |
| Hidden or unfocused conversation | No spinner redraw; preserve state and batch presentation until focus returns. |
| Growing history | Repeated active-item updates should remain nearly constant cost as closed history grows from 1,000 to 10,000 items. Cache eviction and pagination should bound memory. |
| Memory | Set separate process-footprint budgets after a working release build. A provisional client-only target is under 100 MiB for Rust and under 250 MiB for TS with 10,000 synthetic items, excluding image caches, terminal, backend, and providers. These are admission thresholds, not claims about present clients. |
| Energy | No numeric saving target until repeated paired runs establish variance. Accept a claimed improvement only if the measured difference exceeds run-to-run noise and the workload and completion time match. |

## Measurement that can answer the battery question

1. Record exact release build, CPU architecture, terminal, viewport, screen brightness and refresh rate, battery/AC state, thermal state, Low Power Mode, provider state, and fixture. Keep background apps steady. Use synthetic or approved redacted recordings, never a new live model answer for each variant.
2. Measure desktop and TUI with the same backend and replayed event schedule. Include idle with an empty thread, idle with a completed long thread, 20/100/500 updates per second, large tool output, scrolling, rapid typing, resize, and hidden-window cases. The high-rate cases are explicit stress tests. Also measure one representative real provider workflow separately.
3. Attribute cumulative CPU-time deltas over a fixed interval to frontend, server, telemetry monitor, provider trees, and terminal. Report CPU as a fraction of one core. For this 10-core Mac, 100% of one core and 100% of the whole machine are different quantities. RSS is useful for individual processes but summing shared pages across Electron processes can overstate unique memory; also record macOS physical footprint or memory pressure where available.
4. Use the installed `powermetrics` help to choose supported task, wakeup, CPU-power, and GPU-power samplers. This Mac's installed manual says the power figures are estimates, may be inaccurate, and should not be compared across devices. CPU/GPU/ANE subsystem power is not a per-app whole-machine wattmeter. Use it for paired observations on the same Mac, together with process activity. Apple's documentation recommends Activity Monitor and powermetrics for investigation. [Apple measurement guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringEnergyUsage.html), [Apple powermetrics discussion](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html).
5. Alternate randomized A/B or ABBA runs after warmup, at least five pairs. Use 5-10 minute windows for stable idle and streaming comparisons; use longer battery-discharge windows when changes are small. Report medians, spread, sample count, and total energy per completed fixed task. Lower instantaneous power can still consume more energy if completion takes longer.
6. For battery drain, use a sustained, unchanged workload and battery telemetry over enough time to overcome coarse charge readings. Whole-machine battery energy change divided by elapsed hours gives average watts if the energy readings are available. A one-percent charge change over a minute is too coarse for a reliable app estimate. On AC, an external power meter includes adapter losses and battery charging unless those are controlled. Label the measurement boundary.
7. Diagnose unexplained activity with a CPU profile and wakeup trace. Disable one candidate at a time in an isolated build and repeat the paired measurement. Apple's timer guidance explains why idle wakeups matter and recommends event notifications, canceled timers, and appropriate tolerances. It does not establish that four wakeups per second alone explain this screenshot. [Apple timer guidance](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html).

The highest-value first changes are the completed-label clock, the unconditional Rust redraw loop if Tria is used, and per-item cached transcript layout. Then benchmark a release TUI against the desktop before committing to another language or a server rewrite.
